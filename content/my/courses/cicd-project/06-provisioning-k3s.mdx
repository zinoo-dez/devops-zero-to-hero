# Preparing Your Production Server

ဒီ Lesson မှာတော့ ပထမဆုံး deployment မလုပ်ခင် VPS ပေါ်မှာ လုပ်ဆောင်ရမယ့် အရာမှန်သမျှကို ရှင်းပြပေးသွားမှာ ဖြစ်ပါတယ်။ Server တစ်လုံးကို လုံခြုံရေးအရ သေချာပြင်ဆင်ထားခြင်း (Hardened) ဟာ လုံခြုံတဲ့ production system တစ်ခုအတွက် အခြေခံအုတ်မြစ် ဖြစ်ပါတယ်။ ဒီအဆင့်ကို ကျော်သွားတာဟာ Live တက်ပြီး နာရီပိုင်းအတွင်းမှာပဲ server ကို ဟက်ခံရနိုင်ခြေရှိတဲ့ အဖြစ်များဆုံး အမှားတစ်ခု ဖြစ်ပါတယ်။

ဒီ Lesson ပြီးသွားတဲ့အခါမှာ အောက်ပါတို့ အဆင်သင့် ဖြစ်နေပါလိမ့်မယ်။
- လုံခြုံရေးပြင်ဆင်ထားပြီးသား Ubuntu 22.04 VPS တစ်လုံး
- Install လုပ်ပြီး စစ်ဆေးပြီးသား K3s
- ကိုယ့် Laptop ကနေ လှမ်းသုံးလို့ရမယ့် Remote `kubectl` access
- GitHub Actions CD အတွက် Configure လုပ်ထားတဲ့ SSH key-based authentication
- Let's Encrypt `ClusterIssuer` နဲ့တကွ install လုပ်ပြီးသား `cert-manager`

## Step 1: Provision Your VPS

ဒီ Guide မှာတော့ ဈေးအသက်သာဆုံးဖြစ်တဲ့ **Hetzner Cloud** ကို သုံးသွားမှာ ဖြစ်ပေမယ့် အဆင့်တွေက ဘယ် Cloud Provider (DigitalOcean, AWS, Linode) မှာမဆို အတူတူပါပဲ။

### Create the Server

Hetzner Cloud Console မှာ:
1. New server → Location: ကိုယ့် ဒေသနဲ့နီးတဲ့ နေရာ
2. Image: **Ubuntu 22.04 LTS**
3. Type: **CX22** (2 vCPU, 4 GB RAM, 40 GB disk)
4. SSH Key: ကိုယ့်ရဲ့ `~/.ssh/id_ed25519.pub` ကို Add လုပ်ပါ
5. Firewall: Firewall အသစ်တစ်ခု ဖန်တီးပါ (အောက်မှာ ဆက်ပြထားတဲ့အတိုင်း configure လုပ်ပါ)
6. Create server

Public IP address ကို မှတ်ထားပေးပါ — ဒီ Lesson တစ်ခုလုံးမှာ အဲ့ဒါကို သုံးရပါမယ်။

### Configure the Firewall

တကယ်လိုတဲ့ Port တွေကိုပဲ ဖွင့်ပါ:

| Port | Protocol | Source | Purpose |
|------|----------|--------|---------|
| 22 | TCP | Your IP only | SSH access |
| 80 | TCP | Anywhere | HTTP (Traefik) |
| 443 | TCP | Anywhere | HTTPS (Traefik) |
| 6443 | TCP | Your IP only | Kubernetes API server |

<Callout type="caution" title="Restrict Port 22 to Your IP">
Internet တစ်ခုလုံးအတွက် SSH ကို ဖွင့်ထားခဲ့မယ်ဆိုရင် အလိုအလျောက် တိုက်ခိုက်တဲ့ brute-force attacks တွေနဲ့ ကြုံတွေ့ရနိုင်ပါတယ်။ Port 22 ကို ကိုယ့်ရဲ့ Home သို့မဟုတ် Office IP မှာပဲ သုံးလို့ရအောင် VPS provider ရဲ့ firewall ထဲမှာ သတ်မှတ်ပေးပါ။ ကိုယ့် IP ပြောင်းသွားရင် firewall rule ကို ပြန်ပြင်ပေးပါ (သို့မဟုတ်) Bastion host ကို သုံးပါ။
</Callout>

## Step 2: Harden the Server

Root user နဲ့ ကိုယ့် server အသစ်ထဲကို SSH ဝင်ပြီး ဒီ hardening အဆင့်တွေကို Run ပါ:

```bash
ssh root@YOUR_VPS_IP
```

### Create a Non-Root Admin User

```bash
# User အသစ်တစ်ခု ဖန်တီးပါ
adduser deploy
# (Password ခိုင်မာတာတစ်ခုပေးပါ၊ ကျန်တဲ့ Field တွေမှာတော့ Enter ဆက်တိုက်နှိပ်ပြီး ကျော်သွားလို့ရပါတယ်)

# Sudo privileges ပေးပါ
usermod -aG sudo deploy

# Root ရဲ့ authorized SSH keys တွေကို user အသစ်ဆီ ကူးပေးပါ
mkdir -p /home/deploy/.ssh
cp ~/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
```

### Configure SSH Security

```bash
# SSH daemon config ကို Edit လုပ်ပါ
nano /etc/ssh/sshd_config
```

ဒီ Values တွေကို ထည့်ပါ:
```bash
# /etc/ssh/sshd_config — security hardening

# SSH ကနေ root နဲ့ login ဝင်တာကို ပိတ်ပါ (အဲ့ဒီအစား 'deploy' user ကို သုံးပါ)
PermitRootLogin no

# Password authentication ကို ပိတ်ပါ (SSH keys နဲ့ပဲ ဝင်ခွင့်ပြုမယ်)
PasswordAuthentication no
ChallengeResponseAuthentication no

# X11 forwarding ကို ပိတ်ပါ (Server အတွက် မလိုပါဘူး)
X11Forwarding no

# သတ်မှတ်ထားတဲ့ user တွေကိုပဲ ဝင်ခွင့်ပြုမယ်
AllowUsers deploy

# Idle ဖြစ်နေတဲ့ Session တွေကို ဖြတ်ပစ်ဖို့ Timeout ကို လျှော့ချပါ
ClientAliveInterval 300
ClientAliveCountMax 2
```

```bash
# ပြောင်းလဲမှုတွေ သက်ရောက်သွားအောင် SSH ကို Restart ချပါ
systemctl restart sshd

# လက်ရှိ Session ကို မပိတ်ခင် Terminal Tab အသစ်တစ်ခုဖွင့်ပြီး စမ်းကြည့်ပါ:
ssh deploy@YOUR_VPS_IP
# အလုပ်လုပ်ရပါမယ်။ အလုပ်လုပ်တယ်ဆိုရင်တော့ root login ပိတ်သွားပါပြီ။
```

### Configure Automatic Security Updates

```bash
# unattended-upgrades ကို Install လုပ်ပါ
apt-get update
apt-get install -y unattended-upgrades

# Automatic security updates ကို Enable လုပ်ပါ
dpkg-reconfigure -plow unattended-upgrades
# Select: Yes

# Properly configure ဖြစ်မဖြစ် စစ်ဆေးပါ
cat /etc/apt/apt.conf.d/20auto-upgrades
# APT::Periodic::Update-Package-Lists "1";
# APT::Periodic::Unattended-Upgrade "1";
```

### Install Required Tools

```bash
apt-get install -y \
  curl \
  wget \
  git \
  htop \
  jq \
  net-tools \
  ufw    # Simple firewall wrapper (optional, VPS-level firewall မသုံးဘူးဆိုမှ သုံးပါ)
```

## Step 3: Install K3s

K3s ကို Command တစ်ခုတည်းနဲ့ Install လုပ်လို့ရပါတယ်။ သူက Kubernetes API server အပြည့်အစုံ၊ etcd (သို့မဟုတ် SQLite)၊ kubelet၊ kube-proxy၊ CoreDNS နဲ့ Traefik တို့ကို Binary တစ်ခုတည်းနဲ့ အကုန် Setup လုပ်ပေးပါတယ်။

```bash
# Deploy user ထဲကို ပြောင်းဝင်ပါ
su - deploy

# K3s ကို Install လုပ်ပါ (Latest stable version)
curl -sfL https://get.k3s.io | sh -s - \
  --disable traefik \           # Control ပိုချုပ်လို့ရအောင် Traefik ကို သီးသန့် install လုပ်မှာပါ
  --write-kubeconfig-mode 644   # Non-root user တွေပါ kubeconfig ကို ဖတ်လို့ရအောင် လုပ်တာပါ

# K3s စတင်ဖို့ စောင့်ပါ (စက္ကန့် ၃၀ ကနေ ၆၀ လောက် ကြာတတ်ပါတယ်)
sudo systemctl status k3s

# Node ဟာ Ready ဖြစ်မဖြစ် စစ်ဆေးပါ
sudo k3s kubectl get nodes
# NAME        STATUS   ROLES                  AGE   VERSION
# your-vps    Ready    control-plane,master   1m    v1.29.x+k3s1
```

<Callout type="tip" title="Why Disable Traefik in the Installer?">
K3s က Default အနေနဲ့ Traefik 2.x ပါလာပါတယ်။ Install လုပ်တဲ့အချိန်မှာ အဲ့ဒါကို Disable လုပ်လိုက်လို့ ကျွန်တော်တို့ရဲ့ ကိုယ်ပိုင် values file သုံးပြီး Traefik ကို Helm နဲ့ Install လုပ်နိုင်မှာ ဖြစ်ပါတယ်။ ဒါကြောင့် IngressClass settings၊ dashboard access နဲ့ middleware configuration တွေအပေါ်မှာ အပြည့်အဝ ထိန်းချုပ်ခွင့် ရရှိစေပါတယ်။
</Callout>

### Install Traefik via Helm

```bash
# Helm ကို Install လုပ်ပါ
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Traefik Helm repository ကို Add လုပ်ပါ
helm repo add traefik https://traefik.github.io/charts
helm repo update

# Traefik အတွက် values file တစ်ခု ဖန်တီးပါ
cat > /tmp/traefik-values.yaml << 'EOF'
deployment:
  replicas: 1

ingressClass:
  enabled: true
  isDefaultIngressClass: true  # Ingress object အားလုံးက Traefik ကို Default အနေနဲ့ သုံးမယ်

ports:
  web:
    port: 8000
    exposedPort: 80
    redirectTo:
      port: websecure           # HTTP အားလုံးကို HTTPS ဆီ Redirect လုပ်မယ်
  websecure:
    port: 8443
    exposedPort: 443
    tls:
      enabled: true

# Prometheus metrics တွေကို Enable လုပ်ပါ (Lesson 10 မှာ သုံးပါမယ်)
metrics:
  prometheus:
    enabled: true

# Dashboard (kubectl port-forward သုံးပြီး Local ကနေ လှမ်းဝင်ဖို့)
dashboard:
  enabled: true

logs:
  general:
    level: WARN               # Production မှာ Log တွေ ရှုပ်မနေအောင် လျှော့ထားတာပါ
EOF

# Traefik ကို သူ့ရဲ့ Namespace သီးသန့်နဲ့ Install လုပ်ပါ
kubectl create namespace traefik
helm install traefik traefik/traefik \
  -n traefik \
  -f /tmp/traefik-values.yaml

# Traefik Running ဖြစ်နေပြီလား စစ်ဆေးပါ
kubectl -n traefik get pods
# NAME                       READY   STATUS    RESTARTS   AGE
# traefik-xxxxx              1/1     Running   0          30s
```

## Step 4: Configure Remote kubectl Access

ကိုယ့် Laptop ကနေရော (GitHub Actions ကနေပါ) `kubectl` commands တွေကို Run နိုင်ဖို့ လိုပါတယ်။

```bash
# VPS ပေါ်မှာ: kubeconfig ကို ယူပါ
sudo cat /etc/rancher/k3s/k3s.yaml
```

Output ကို Copy ကူးပါ။ ကိုယ့်ရဲ့ **Local Machine** မှာ:

```bash
# .kube directory မရှိသေးရင် ဖန်တီးပါ
mkdir -p ~/.kube

# Kubeconfig ကို Paste လုပ်ပါ (Content အဟောင်းကို အစားထိုးပါ)
nano ~/.kube/config

# အရေးကြီးသည်: Server address ကို အောက်ပါအတိုင်း ပြောင်းပါ
#   server: https://127.0.0.1:6443
# မှ:
#   server: https://YOUR_VPS_IP:6443

# Local access အလုပ်လုပ်မလုပ် စစ်ဆေးပါ
kubectl get nodes
# NAME        STATUS   ROLES                  AGE   VERSION
# your-vps    Ready    control-plane,master   5m    v1.29.x+k3s1
```

### Store the Kubeconfig as a GitHub Secret

CD Workflow (Lesson 8) က ကိုယ့် Cluster ပေါ်မှာ `kubectl` commands တွေ Run ဖို့ လိုအပ်ပါတယ်။

```bash
# ကိုယ့် Local Machine မှာ: kubeconfig ကို base64 အဖြစ် encode လုပ်ပါ
cat ~/.kube/config | base64 | tr -d '\n'
# (output ကို Copy ကူးပါ — အဲ့ဒါ Base64 string ရှည်ကြီးတစ်ခု ဖြစ်ပါတယ်)
```

GitHub Secret အနေနဲ့ Add လုပ်ပါ:
1. Repository → Settings → Secrets and variables → Actions
2. New repository secret: `KUBECONFIG_BASE64` = (base64 string ကို Paste လုပ်ပါ)

## Step 6: Install cert-manager

cert-manager က Let's Encrypt ကနေ TLS certificate တွေကို အလိုအလျောက် ထုတ်ပေးပါတယ်။ သူက `Certificate` နဲ့ `Ingress` resources တွေကို စောင့်ကြည့်နေပြီး Certificates တွေကို အလိုအလျောက် ထုတ်ပေး/သက်တမ်းတိုးပေးပါတယ်။

```bash
# Helm သုံးပြီး cert-manager ကို Install လုပ်ပါ
helm repo add jetstack https://charts.jetstack.io
helm repo update

kubectl create namespace cert-manager

helm install cert-manager jetstack/cert-manager \
  -n cert-manager \
  --version v1.14.4 \
  --set installCRDs=true \
  --set prometheus.enabled=true   # Lesson 10 အတွက် Metrics ကို Enable လုပ်ပါ

# cert-manager pods တွေ Running ဖြစ်မဖြစ် စစ်ဆေးပါ (စက္ကန့် ၃၀ ကနေ ၆၀ ကြာပါတယ်)
kubectl -n cert-manager get pods
# NAME                                      READY   STATUS    RESTARTS
# cert-manager-xxx                          1/1     Running   0
# cert-manager-cainjector-xxx               1/1     Running   0
# cert-manager-webhook-xxx                  1/1     Running   0
```

### Create the Let's Encrypt ClusterIssuer

`ClusterIssuer` ဆိုတာ cert-manager က certificate တွေကို ဘယ်လိုရယူရမယ်ဆိုတာကို ညွှန်ပြပေးတဲ့ cert-manager resource တစ်ခု ဖြစ်ပါတယ်။ သူက Cluster တစ်ခုလုံးအတွက် သက်ရောက်ပါတယ် (namespace တစ်ခုတည်းအတွက် မဟုတ်ပါ)၊ ဒါကြောင့် Namespace အားလုံးက သုံးလို့ရပါတယ်။

```yaml
# clusterissuer-letsencrypt.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # Let's Encrypt production endpoint
    # Rate limited: Domain တစ်ခုကို တစ်ပတ်မှ 50 certificates ပဲ ရမယ်
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@example.com  # ← ကိုယ့်အီးမေးလ်နဲ့ အစားထိုးပါ (သက်တမ်းကုန်မယ့် သတိပေးချက်တွေ ပို့ဖို့ သုံးပါတယ်)
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: traefik  # HTTP challenge solver အနေနဲ့ Traefik ကို သုံးမယ်
```

```yaml
# clusterissuer-letsencrypt-staging.yaml
# Testing လုပ်နေတုန်း Rate limit ပြဿနာ မတက်အောင် ဒါကို အရင်သုံးပါ
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    email: your-email@example.com
    privateKeySecretRef:
      name: letsencrypt-staging-account-key
    solvers:
      - http01:
          ingress:
            class: traefik
```

```bash
# Issuers နှစ်ခုစလုံးကို Apply လုပ်ပါ
kubectl apply -f clusterissuer-letsencrypt.yaml
kubectl apply -f clusterissuer-letsencrypt-staging.yaml

# Ready ဖြစ်မဖြစ် စစ်ဆေးပါ
kubectl get clusterissuer
# NAME                    READY   AGE
# letsencrypt-prod        True    30s
# letsencrypt-staging     True    30s
```

<Callout type="warning" title="Always Test with Staging First">
Let's Encrypt production မှာ Rate limits ရှိပါတယ်: Register လုပ်ထားတဲ့ Domain တစ်ခုကို တစ်ပတ်မှ Certificate 50 ခုပဲ ရပါတယ်။ Debug လုပ်နေတုန်း Limit ပြည့်သွားရင် ၇ ရက်တိတိ အသစ်ထပ်ယူလို့ မရတော့ပါဘူး။ Development လုပ်နေစဉ် Staging `ClusterIssuer` ကိုပဲ သုံးပါ — Staging certificates တွေကို Browser တွေက မယုံကြည်ကြပေမယ့် Certificate ထုတ်ပေးတဲ့ Flow ကို Test ဖို့အတွက်တော့ အတူတူပါပဲ။
</Callout>

## Step 7: Create the Deploy SSH Key for GitHub Actions

CD Workflow က `kubectl apply` Run ဖို့ သို့မဟုတ် Image Update လုပ်ဖို့ Server ထဲကို SSH ဝင်နိုင်ဖို့ လိုပါတယ်။ Deploy key သီးသန့်တစ်ခု ဖန်တီးပါ:

```bash
# ကိုယ့် LOCAL machine မှာ: Deploy key သီးသန့်တစ်ခု ဖန်တီးပါ (Passphrase မပါပါ)
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/deploy_key -N ""

# Public key ကို Server ဆီ ကူးပေးပါ
ssh-copy-id -i ~/.ssh/deploy_key.pub deploy@YOUR_VPS_IP

# (သို့မဟုတ်) လက်ဖြင့် လုပ်ချင်ရင်:
cat ~/.ssh/deploy_key.pub | ssh deploy@YOUR_VPS_IP \
  "cat >> ~/.ssh/authorized_keys"
```

Private key ကို GitHub Secret အနေနဲ့ Add လုပ်ပါ:
```bash
# Private key ကို ထုတ်ပြပါ
cat ~/.ssh/deploy_key
# (BEGIN နဲ့ END စာကြောင်းတွေ အပါအဝင် Output တစ်ခုလုံးကို Copy ကူးပါ)
```

Repository → Settings → Secrets → New:
- `SSH_PRIVATE_KEY` = (Private key ကို Paste လုပ်ပါ)
- `SSH_HOST` = `YOUR_VPS_IP`
- `SSH_USER` = `deploy`

```bash
# ချိတ်ဆက်မှု အလုပ်လုပ်မလုပ် စစ်ဆေးပါ (GitHub Actions က ဒါကို သုံးပါလိမ့်မယ်)
ssh -i ~/.ssh/deploy_key deploy@YOUR_VPS_IP "kubectl get nodes"
# NAME        STATUS   ROLES                  AGE
# your-vps    Ready    control-plane,master   20m
```

## Understanding the K3s Architecture

K3s က Control plane နဲ့ Data plane ကို ပေါင်းစပ်ထားတဲ့ Single binary အနေနဲ့ (Single-node cluster တစ်ခုပေါ်မှာ) Run ပါတယ်။

```mermaid
flowchart TD
    subgraph vps["VPS — Single Node K3s"]
        subgraph k3s["k3s binary"]
            API[API Server\n:6443]
            ETCD[SQLite\n(embedded etcd replacement)]
            SCHED[Scheduler]
            CM[Controller Manager]
        end
        subgraph node["Node Agent"]
            KUBELET[kubelet]
            KPROXY[kube-proxy]
        end
        subgraph network["Networking"]
            FLANNEL[Flannel CNI\n(pod network)]
            COREDNS[CoreDNS\n(cluster DNS)]
            TRAEFIK[Traefik\n(ingress)]
        end
        subgraph storage["Storage"]
            LOCALPATH[local-path-provisioner\n(PVC → hostPath)]
        end
    end

    LAPTOP[Your Laptop\nkubectl --server=VPS:6443]
    GH_ACTIONS[GitHub Actions\nkubectl set image]

    LAPTOP -->|6443 TLS| API
    GH_ACTIONS -->|SSH tunnel or 6443| API
    API --> ETCD
    API --> SCHED
    API --> CM
    KUBELET -->|reports status| API
    KUBELET --> FLANNEL
    KUBELET --> COREDNS
    KUBELET --> TRAEFIK

```

K3s ဟာ Default အနေနဲ့ etcd အစား **SQLite** ကို သုံးပါတယ်။ Single-node cluster တစ်ခုအတွက် ဒါက အဆင်ပြေပါတယ်။ Multi-node HA အတွက်ဆိုရင်တော့ Embedded etcd သို့မဟုတ် External database ကို သုံးရပါမယ်။

## Troubleshooting Common Issues

### K3s စတင်လို့ မရဘူး
```bash
# Logs တွေကို စစ်ဆေးပါ
sudo journalctl -u k3s -f --no-pager

# အဖြစ်များတဲ့ ဖြေရှင်းနည်း: Port 6443 နဲ့ 10250 တွေကို Firewall က ပိတ်ထားခြင်း မရှိကြောင်း သေချာပါစေ
sudo ss -tlnp | grep 6443
```

### Kubernetes API ကို "Connection refused" ဖြစ်နေတယ်
```bash
# K3s API server Listen လုပ်နေမနေ စစ်ဆေးပါ
curl -k https://YOUR_VPS_IP:6443/healthz
# ok

# Firewall က သင့် IP ကနေ Port 6443 ကို ဝင်ခွင့်ပေးထားမပေး စစ်ဆေးပါ
ufw status  # (သို့မဟုတ် VPS provider ရဲ့ firewall rules တွေကို စစ်ပါ)
```

### cert-manager webhook Error တက်နေတယ်
```bash
kubectl -n cert-manager describe pod -l app=cert-manager-webhook
# အများအားဖြင့် Timing ပြဿနာပါ — စက္ကန့် ၆၀ လောက်စောင့်ပြီး ထပ်ကြိုးစားပါ
```

## Summary

သင့်ရဲ့ Production server အဆင်သင့် ဖြစ်သွားပါပြီ:
- **Ubuntu 22.04** ကို SSH key-only auth၊ root login ပိတ်ထားခြင်း၊ automatic security updates တွေနဲ့ လုံခြုံရေးပြင်ဆင်ပြီးသား
- **K3s** ကို Traefik ingress controller နဲ့တကွ Install ပြီးသား (K3s default ကို မသုံးဘဲ Helm နဲ့ သွင်းထားတာပါ)
- **Remote `kubectl` access** ကို Laptop ကနေ သုံးလို့ရအောင် လုပ်ထားပြီး GitHub Secret အနေနဲ့ သိမ်းဆည်းပြီးသား
- **cert-manager** မှာ Staging နဲ့ Production Let's Encrypt `ClusterIssuers` နှစ်ခုစလုံး ပါဝင်ပြီးသား
- **`production` namespace** ဖန်တီးပြီး Label တပ်ပြီးသား
- **Deploy SSH key** ကို Server ပေါ် တင်ထားပြီး GitHub Secrets ထဲမှာ ထည့်ပြီးသား

နောက် Lesson မှာတော့ သင့်ရဲ့ Application ရဲ့ လိုချင်တဲ့ ပုံစံ (Desired state) ကို Cluster ထဲမှာ သတ်မှတ်ပေးမယ့် Kubernetes manifests တွေကို (Deployment, Service, Ingress, ConfigMap, Secret) ရေးသားသွားမှာ ဖြစ်ပါတယ်။
