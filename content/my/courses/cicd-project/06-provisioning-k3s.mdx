# သင်၏ထုတ်လုပ်ရေးဆာဗာကို ပြင်ဆင်ခြင်း

ဤသင်ခန်းစာတွင် ပထမဆုံးအကြိမ် deployment မလုပ်မီ VPS ပေါ်တွင် သင်လုပ်ဆောင်ရမည့်အရာအားလုံးကို အကျုံးဝင်စေမည် ဖြစ်ပါသည်။ စနစ်တကျ လုံခြုံရေးမြှင့်တင်ထားသော ဆာဗာတစ်ခုသည် လုံခြုံသော ထထုတ်လုပ်ရေးစနစ် (production system) တစ်ခုအတွက် အခြေခံအုတ်မြစ် ဖြစ်ပါသည်။ ဤအဆင့်ကို ကျော်သွားခြင်းသည် လွှင့်တင်ပြီး နာရီပိုင်းအတွင်းမှာပင် ဆာဗာများ ဟက်ခံရနိုင်သည့် အဖြစ်များသော အမှားတစ်ခု ဖြစ်ပါသည်။

ဤသင်ခန်းစာ ပြီးဆုံးချိန်တွင် သင်၌ အောက်ပါတို့ ရှိလာမည် ဖြစ်သည်-
- လုံခြုံရေးမြှင့်တင်ထားသော Ubuntu 22.04 VPS တစ်ခု
- ထည့်သွင်းပြီး အတည်ပြုပြီးသား K3s
- သင့်လက်ပ်တော့မှ လှမ်းသုံးနိုင်သော Remote `kubectl` အသုံးပြုခွင့်
- GitHub Actions စီဒီ (CD) အတွက် ပြင်ဆင်ထားသော SSH key အခြေခံသည့် အတည်ပြုခြင်းစနစ် (authentication)
- Let's Encrypt ClusterIssuer ပါရှိသော cert-manager ကို ထည့်သွင်းထားခြင်း

---

## အဆင့် ၁ - သင်၏ VPS ကို ပြင်ဆင်ပါ (Provision Your VPS)

ဤလမ်းညွှန်ချက်တွင် **Hetzner Cloud** (ဈေးအသက်သာဆုံး) ကို အသုံးပြုထားသော်လည်း အဆင့်များသည် မည်သည့် ပံ့ပိုးပေးသူ (DigitalOcean, AWS, Linode) မဆို အတူတူပင် ဖြစ်ပါသည်။

### ဆာဗာကို ဖန်တီးပါ

Hetzner Cloud Console ပေါ်တွင်:
1. New server → Location: သင်၏ဒေသ (region)
2. Image: **Ubuntu 22.04 LTS**
3. Type: **CX22** (2 vCPU, 4 GB RAM, 40 GB disk)
4. SSH Key: သင့်ရဲ့ `~/.ssh/id_ed25519.pub` ကို ထည့်ပါ
5. Firewall: Firewall အသစ်တစ်ခု ဖန်တီးပါ (အောက်တွင် ပြင်ဆင်ထားသည်)
6. Create server ကို နှိပ်ပါ

Public IP လိပ်စာကို မှတ်ထားပါ — ဤသင်ခန်းစာတစ်လျှောက်လုံးတွင် ၎င်းကို သင်အသုံးပြုရပါမည်။

### ဖိုင်းဝေါကို ပြင်ဆင်ပါ (Configure the Firewall)

သင် အမှန်တကယ် လိုအပ်သော ပေါ့တ် (ports) များကိုသာ ဖွင့်ပါ:

| Port | Protocol | Source | Purpose |
|------|----------|--------|---------|
| 22 | TCP | Your IP only | SSH access |
| 80 | TCP | Anywhere | HTTP (Traefik) |
| 443 | TCP | Anywhere | HTTPS (Traefik) |
| 6443 | TCP | Your IP only | Kubernetes API server |

<Callout type="caution" title="Restrict Port 22 to Your IP">
SSH ကို အင်တာနက် တစ်ခုလုံးအတွက် ဖွင့်ထားခြင်းသည် အလိုအလျောက် စကားဝှက်ရမ်းရိုက်တိုက်ခိုက်မှုများ (brute-force attacks) ကို ဖြစ်စေနိုင်ပါသည်။ ပေါ့တ် ၂၂ ကို သင့်အိမ်/ရုံး IP သို့သာ ကန့်သတ်ရန် သင်၏ VPS ပံ့ပိုးပေးသူ၏ ဖိုင်းဝေါကို အသုံးပြုပါ။ သင့် IP ပြောင်းလဲသွားပါက ဖိုင်းဝေါ စည်းမျဉ်းကို အပ်ဒိတ်လုပ်ပါ — သို့မဟုတ် bastion host တစ်ခုကို အသုံးပြုပါ။
</Callout>

## အဆင့် ၂ - ဆာဗာ လုံခြုံရေးမြှင့်တင်ပါ (Harden the Server)

root အနေဖြင့် သင်၏ ဆာဗာအသစ်သို့ SSH ဖြင့် ဝင်ရောက်ပြီး ဤလုံခြုံရေး အဆင့်များကို လုပ်ဆောင်ပါ:

```bash
ssh root@YOUR_VPS_IP
```

### Root မဟုတ်သော အက်မင် အသုံးပြုသူတစ်ဦးကို ဖန်တီးပါ (Create a Non-Root Admin User)

```bash
# အသုံးပြုသူအသစ် ဖန်တီးရန်
adduser deploy
# (ခိုင်မာသော စကားဝှက်တစ်ခု ထည့်ပါ၊ အခြားကွက်လပ်များကို ဖြည့်ပါ သို့မဟုတ် ကျော်သွားရန် Enter နှိပ်ပါ)

# sudo အခွင့်အရေး ပေးရန်
usermod -aG sudo deploy

# root ၏ ခွင့်ပြုထားသော SSH გასაღေ့များကို အသုံးပြုသူအသစ်ထံ ကူးယူရန်
mkdir -p /home/deploy/.ssh
cp ~/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh
chmod 600 /home/deploy/.ssh/authorized_keys
```

### SSH လုံခြုံရေးကို ပြင်ဆင်ပါ (Configure SSH Security)

```bash
# SSH daemon config ကို တည်းဖြတ်ရန်
nano /etc/ssh/sshd_config
```

ဤတန်ဖိုးများကို သတ်မှတ်ပါ:
```bash
# /etc/ssh/sshd_config — security hardening

# SSH မှတစ်ဆင့် root ဖြင့် ဝင်ရောက်မှုကို ပိတ်ပါ (အစား 'deploy' အသုံးပြုသူကို သုံးပါ)
PermitRootLogin no

# စကားဝှက်ဖြင့် အတည်ပြုခြင်းကို ပိတ်ပါ (SSH გასაღებებიသာ သုံးရန်)
PasswordAuthentication no
ChallengeResponseAuthentication no

# X11 forwarding ကို ပိတ်ပါ (ဆာဗာအတွက် မလိုအပ်ပါ)
X11Forwarding no

# သီးခြား အသုံးပြုသူများကိုသာ ခွင့်ပြုရန်
AllowUsers deploy

# အသုံးမပြုဘဲ ရပ်နေသော ဆက်ရှင်များကို ဖြတ်ရန် အချိန်ကို လျှော့ချပါ
ClientAliveInterval 300
ClientAliveCountMax 2
```

```bash
# အပြောင်းအလဲများ အသက်ဝင်စေရန် SSH ကို ပြန်လည်စတင်ပါ
systemctl restart sshd

# လက်ရှိဆက်ရှင်ကို မပိတ်မီ တာမီနယ် တက်ဘ်အသစ်တွင် စမ်းသပ်ပါ:
ssh deploy@YOUR_VPS_IP
# အလုပ်လုပ်သင့်သည်။ အကယ်၍ အလုပ်လုပ်ပါက root ဖြင့် ဝင်ရောက်မှုကို ယခု ပိတ်ပြီးပါပြီ။
```

### အလိုအလျောက် လုံခြုံရေး အပ်ဒိတ်များကို ပြင်ဆင်ပါ (Configure Automatic Security Updates)

```bash
# unattended-upgrades ကို ထည့်သွင်းရန်
apt-get update
apt-get install -y unattended-upgrades

# အလိုအလျောက် လုံခြုံရေး အပ်ဒိတ်များကို ဖွင့်ရန်
dpkg-reconfigure -plow unattended-upgrades
# Select: Yes

# ပြင်ဆင်ပြီးဖြစ်ကြောင်း အတည်ပြုရန်
cat /etc/apt/apt.conf.d/20auto-upgrades
# APT::Periodic::Update-Package-Lists "1";
# APT::Periodic::Unattended-Upgrade "1";
```

### လိုအပ်သော ကိရိယာများကို ထည့်သွင်းပါ (Install Required Tools)

```bash
apt-get install -y \
  curl \
  wget \
  git \
  htop \
  jq \
  net-tools \
  ufw    # Simple firewall wrapper (optional, use if not using VPS-level firewall)
```

## အဆင့် ၃ - K3s ကို ထည့်သွင်းပါ (Install K3s)

K3s ကို အမိန့်တစ်ကြောင်းတည်းဖြင့် ထည့်သွင်းနိုင်ပါသည်။ ၎င်းသည် Kubernetes API server အပြည့်အစုံ၊ etcd (သို့မဟုတ် SQLite)၊ kubelet၊ kube-proxy၊ CoreDNS နှင့် Traefik တို့ကို binary တစ်ခုတည်းတွင် အားလုံး စနစ်ထည့်သွင်းပေးပါသည်။

```bash
# deploy အသုံးပြုသူသို့ ပြောင်းရန်
su - deploy

# K3s ကို ထည့်သွင်းရန် (နောက်ဆုံးထွက် တည်ငြိမ်သောဗားရှင်း)
curl -sfL https://get.k3s.io | sh -s - \
  --disable traefik \           # ပိုမိုထိန်းချုပ်နိုင်ရန် Traefik ကို သီးသန့်ထည့်သွင်းပါမည်
  --write-kubeconfig-mode 644   # root မဟုတ်သူများ kubeconfig ကို ဖတ်ရှုခွင့်ပြုရန်

# K3s စတင်ရန် စောင့်ပါ (စက္ကန့် ၃၀-၆၀ ကြာတတ်သည်)
sudo systemctl status k3s

# နုဒ် (node) အဆင်သင့်ဖြစ်ပြီလား စစ်ဆေးရန်
sudo k3s kubectl get nodes
# NAME        STATUS   ROLES                  AGE   VERSION
# your-vps    Ready    control-plane,master   1m    v1.29.x+k3s1
```

<Callout type="tip" title="Why Disable Traefik in the Installer?">
K3s သည် မူလအားဖြင့် Traefik 2.x ပါရှိပြီးသား ဖြစ်ပါသည်။ ထည့်သွင်းစဉ်အတွင်း ၎င်းကို ပိတ်ထားခြင်းဖြင့် Traefik ကို ကျွန်ုပ်တို့၏ ကိုယ်ပိုင် values ဖိုင်ဖြင့် Helm မှတစ်ဆင့် ထည့်သွင်းနိုင်ပြီး IngressClass ဆက်တင်များ၊ ဒက်ရှ်ဘೋರ್ အသုံးပြုခွင့်နှင့် middleware ပြင်ဆင်မှုများကို အပြည့်အဝ ထန်းချုပ်နိုင်မည် ဖြစ်ပါသည်။
</Callout>

### Helm မှတစ်ဆင့် Traefik ကို ထည့်သွင်းပါ

```bash
# Helm ကို ထည့်သွင်းရန်
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Traefik Helm repository ကို ပေါင်းထည့်ရန်
helm repo add traefik https://traefik.github.io/charts
helm repo update

# Traefik အတွက် values ဖိုင်တစ်ခု ဖန်တီးရန်
cat > /tmp/traefik-values.yaml << 'EOF'
deployment:
  replicas: 1

ingressClass:
  enabled: true
  isDefaultIngressClass: true  # All Ingress objects use Traefik by default

ports:
  web:
    port: 8000
    exposedPort: 80
    redirectTo:
      port: websecure           # Redirect all HTTP → HTTPS
  websecure:
    port: 8443
    exposedPort: 443
    tls:
      enabled: true

# Prometheus metrics များကို ဖွင့်ရန် (သင်ခန်းစာ ၁၀ တွင် အသုံးပြုသည်)
metrics:
  prometheus:
    enabled: true

# Dashboard (kubectl port-forward ဖြင့် ဒေသတွင်းတွင် ဝင်သုံးရန်)
dashboard:
  enabled: true

logs:
  general:
    level: WARN               # Reduce log noise in production
EOF

# Traefik ကို ၎င်း၏ ကိုယ်ပိုင် namespace တွင် ထည့်သွင်းရန်
kubectl create namespace traefik
helm install traefik traefik/traefik \
  -n traefik \
  -f /tmp/traefik-values.yaml

# Traefik အလုပ်လုပ်နေကြောင်း အတည်ပြုရန်
kubectl -n traefik get pods
# NAME                       READY   STATUS    RESTARTS   AGE
# traefik-xxxxx              1/1     Running   0          30s
```

## အဆင့် ၄ - Remote kubectl အသုံးပြုခွင့်ကို ပြင်ဆင်ပါ (Configure Remote kubectl Access)

သင်၏ လက်ပ်တော့ (နှင့် GitHub Actions) မှနေ၍ `kubectl` အမိန့်များကို လုပ်ဆောင်ရန် လိုအပ်ပါသည်။

```bash
# VPS ပေါ်တွင်: kubeconfig ကို ရယူရန်
sudo cat /etc/rancher/k3s/k3s.yaml
```

ထွက်လာသော စာသားများကို ကူးယူပါ။ သင်၏ **ဒေသတွင်းစက် (local machine)** ပေါ်တွင်:

```bash
# .kube လမ်းညွှန် မရှိသေးပါက ဖန်တီးရန်
mkdir -p ~/.kube

# kubeconfig ကို ကူးထည့်ပါ (အကြောင်းအရာများကို အစားထိုးပါ)
nano ~/.kube/config

# အရေးကြီးသည်: ဆာဗာလိပ်စာကို ဤသို့ပြောင်းပါ:
#   server: https://127.0.0.1:6443
# မှ ဤသို့:
#   server: https://YOUR_VPS_IP:6443 သို့ ပြောင်းပါ

# ဒေသတွင်း အသုံးပြုခွင့်ကို အတည်ပြုရန်
kubectl get nodes
# NAME        STATUS   ROLES                  AGE   VERSION
# your-vps    Ready    control-plane,master   5m    v1.29.x+k3s1
```

### Kubeconfig ကို GitHub Secret အဖြစ် သိမ်းဆည်းပါ

CD workflow (သင်ခန်းစာ ၈) သည် သင်၏ ကလပ်စတာ (cluster) ကို ဆန့်ကျင်၍ `kubectl` အမိန့်များကို လုပ်ဆောင်ရန် လိုအပ်ပါသည်။

```bash
# သင်၏ ဒေသတွင်းစက်ပေါ်တွင်: kubeconfig ကို base64 ဖြင့် ကုဒ်လုပ်ပါ
cat ~/.kube/config | base64 | tr -d '\n'
# (ထွက်လာသည်ကို ကူးယူပါ — ၎င်းသည် ရှည်လျားသော base64 စာသားတန်းတစ်ခု ဖြစ်သည်)
```

၎င်းကို GitHub Secret အဖြစ် ထည့်ပါ:
1. Repository → Settings → Secrets and variables → Actions
2. New repository secret: `KUBECONFIG_BASE64` = (base64 စာသားတန်းကို ကူးထည့်ပါ)

## အဆင့် ၅ - ထုတ်လုပ်ရေး Namespace ကို ဖန်တီးပါ (Create the Production Namespace)


## အဆင့် ၆ - cert-manager ကို ထည့်သွင်းပါ (Install cert-manager)

cert-manager သည် Let's Encrypt မှ TLS လက်မှတ်ထုတ်ပေးခြင်းကို အလိုအလျောက် လုပ်ဆောင်ပေးပါသည်။ ၎င်းသည် `Certificate` နှင့် `Ingress` ရင်းမြစ်များကို စောင့်ကြည့်ပြီး လက်မှတ်များကို အလိုအလျောက် ထုတ်ပေးခြင်း/သက်တမ်းတိုးခြင်း လုပ်ဆောင်ပေးပါသည်။

```bash
# Helm မှတစ်ဆင့် cert-manager ကို ထည့်သွင်းရန်
helm repo add jetstack https://charts.jetstack.io
helm repo update

kubectl create namespace cert-manager

helm install cert-manager jetstack/cert-manager \
  -n cert-manager \
  --version v1.14.4 \
  --set installCRDs=true \
  --set prometheus.enabled=true   # သင်ခန်းစာ ၁၀ အတွက် metrics ကို ဖွင့်ပါ

# cert-manager pods များ Running ဖြစ်နေကြောင်း အတည်ပြုရန် (စက္ကန့် ၃၀-၆၀ ကြာတတ်သည်)
kubectl -n cert-manager get pods
# NAME                                      READY   STATUS    RESTARTS
# cert-manager-xxx                          1/1     Running   0
# cert-manager-cainjector-xxx               1/1     Running   0
# cert-manager-webhook-xxx                  1/1     Running   0
```

### Let's Encrypt ClusterIssuer ကို ဖန်တီးပါ

`ClusterIssuer` ဆိုသည်မှာ လက်မှတ်များကို မည်သို့ရယူရမည်ကို cert-manager အား ပြောပြပေးသော cert-manager ရင်းမြစ်တစ်ခု ဖြစ်ပါသည်။ ၎င်းသည် namespace အဆင့်မဟုတ်ဘဲ ကလပ်စတာအဆင့် (cluster-scoped) ဖြစ်သောကြောင့် namespace အားလုံးက ၎င်းကို အသုံးပြုနိုင်ပါသည်။

```yaml
# clusterissuer-letsencrypt.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    # Let's Encrypt production endpoint
    # Rate limited: 50 certificates per domain per week
    server: https://acme-v02.api.letsencrypt.org/directory
    email: your-email@example.com  # ← သင့်အီးမေးလ်ဖြင့် အစားထိုးပါ (သက်တမ်းကုန်ဆုံးမည့် သတိပေးချက်များအတွက် သုံးသည်)
    privateKeySecretRef:
      name: letsencrypt-prod-account-key
    solvers:
      - http01:
          ingress:
            class: traefik  # HTTP challenge solver အဖြစ် Traefik ကို သုံးပါ
```

```yaml
# clusterissuer-letsencrypt-staging.yaml
# စမ်းသပ်နေစဉ်အတွင်း rate limit ပြဿနာများကို ရှောင်ရှားရန် ဤဟာကို အရင်သုံးပါ
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-staging
spec:
  acme:
    server: https://acme-staging-v02.api.letsencrypt.org/directory
    email: your-email@example.com
    privateKeySecretRef:
      name: letsencrypt-staging-account-key
    solvers:
      - http01:
          ingress:
            class: traefik
```

```bash
# Issuers နှစ်ခုစလုံးကို အသက်သွင်းရန်
kubectl apply -f clusterissuer-letsencrypt.yaml
kubectl apply -f clusterissuer-letsencrypt-staging.yaml

# Ready ဖြစ်နေကြောင်း အတည်ပြုရန်
kubectl get clusterissuer
# NAME                    READY   AGE
# letsencrypt-prod        True    30s
# letsencrypt-staging     True    30s
```

<Callout type="warning" title="Always Test with Staging First">
Let's Encrypt production တွင် နှုန်းသတ်မှတ်ချက်များ (rate limits) ရှိပါသည်: တစ်ပတ်လျှင် ဒိုမိန်းတစ်ခုအတွက် လက်မှတ် ၅၀ ဖြစ်သည်။ အမှားရှာဖွေနေစဉ် (debugging) ကန့်သတ်ချက်သို့ ရောက်ရှိသွားပါက ရက် ၇ ရက်တိုင်တိုင် လက်မှတ်အသစ်များ ထုတ်ယူ၍မရအောင် ပိတ်ပင်ခံရမည် ဖြစ်ပါသည်။ ဖွံ့ဖြိုးတိုးတက်ရေးအဆင့်တွင် Staging ClusterIssuer ကို အသုံးပြုပါ — စတိတ်ဂျင်း လက်မှတ်များကို ဘရောက်ဆာများက ယုံကြည်မှုမရှိသော်လည်း လက်မှတ်ထုတ်ပေးသည့် စီးဆင်းမှုကို စမ်းသပ်ရန်အတွက်မူ အတူတူပင် အလုပ်လုပ်ပါသည်။
</Callout>

## အဆင့် ၇ - GitHub Actions အတွက် Deploy SSH Key ကို ဖန်တီးပါ

CD workflow သည် `kubectl apply` ကို လုပ်ဆောင်ရန် သို့မဟုတ် ပုံရိပ် အပ်ဒိတ်များကို စတင်ရန် သင့်ဆာဗာသို့ SSH ဖြင့် ဝင်ရောက်ရန် လိုအပ်ပါသည်။ သီးသန့် deploy key တစ်ခုကို ဖန်တီးပါ:

```bash
# သင်၏ ဒေသတွင်းစက်ပေါ်တွင်: သီးသန့် deploy key တစ်ခုကို ဖန်တီးပါ (passphrase မပါဘဲ)
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/deploy_key -N ""

# Public key ကို ဆာဗာသို့ ကူးယူပါ
ssh-copy-id -i ~/.ssh/deploy_key.pub deploy@YOUR_VPS_IP

# သို့မဟုတ် ကိုယ်တိုင်:
cat ~/.ssh/deploy_key.pub | ssh deploy@YOUR_VPS_IP \
  "cat >> ~/.ssh/authorized_keys"
```

Private key ကို GitHub Secret အဖြစ် ထည့်ပါ:
```bash
# Private key ကို ထုတ်ပြပါ
cat ~/.ssh/deploy_key
# (BEGIN နှင့် END လိုင်းများအပါအဝင် အထွက်စာသား အားလုံးကို ကူးယူပါ)
```

Repository → Settings → Secrets → New:
- `SSH_PRIVATE_KEY` = (private key ကို ကူးထည့်ပါ)
- `SSH_HOST` = `YOUR_VPS_IP`
- `SSH_USER` = `deploy`

```bash
# ချိတ်ဆက်မှု အလုပ်လုပ်ကြောင်း စမ်းသပ်ပါ (GitHub Actions က ဤဟာကို သုံးပါလိမ့်မည်)
ssh -i ~/.ssh/deploy_key deploy@YOUR_VPS_IP "kubectl get nodes"
# NAME        STATUS   ROLES                  AGE
# your-vps    Ready    control-plane,master   20m
```

## K3s ဗိသုကာကို နားလည်ခြင်း (Understanding the K3s Architecture)

K3s သည် control plane နှင့် data plane ကို (နုဒ်တစ်ခုတည်းပါသော ကလပ်စတာတွင်) ပေါင်းစပ်ထားသော binary တစ်ခုအနေဖြင့် အလုပ်လုပ်သည်:

```mermaid
flowchart TD
    subgraph vps["VPS — Single Node K3s"]
        subgraph k3s["k3s binary"]
            API[API Server\n:6443]
            ETCD[SQLite\n(embedded etcd replacement)]
            SCHED[Scheduler]
            CM[Controller Manager]
        end
        subgraph node["Node Agent"]
            KUBELET[kubelet]
            KPROXY[kube-proxy]
        end
        subgraph network["Networking"]
            FLANNEL[Flannel CNI\n(pod network)]
            COREDNS[CoreDNS\n(cluster DNS)]
            TRAEFIK[Traefik\n(ingress)]
        end
        subgraph storage["Storage"]
            LOCALPATH[local-path-provisioner\n(PVC → hostPath)]
        end
    end

    LAPTOP[Your Laptop\nkubectl --server=VPS:6443]
    GH_ACTIONS[GitHub Actions\nkubectl set image]

    LAPTOP -->|6443 TLS| API
    GH_ACTIONS -->|SSH tunnel or 6443| API
    API --> ETCD
    API --> SCHED
    API --> CM
    KUBELET -->|reports status| API
    KUBELET --> FLANNEL
    KUBELET --> COREDNS
    KUBELET --> TRAEFIK
    KUBELET --> LOCALPATH
```

K3s သည် မူလအားဖြင့် etcd အစား **SQLite** ကို အသုံးပြုပါသည်။ နုဒ်တစ်ခုတည်းပါသော ကလပ်စတာအတွက် ဤသည်မှာ အဆင်ပြေပါသည်။ နုဒ်များစွာပါသော HA အတွက်ဆိုပါက embedded etcd သို့မဟုတ် အပြင်ဘက် ဒေတာဘေ့စ်တစ်ခုကို အသုံးပြုရပါမည်။

## ဖြစ်လေ့ရှိသော ပြဿနာများကို ဖြေရှင်းခြင်း (Troubleshooting Common Issues)

### K3s စတင်မလာပါ
```bash
# လော့ဂ်များကို စစ်ဆေးရန်
sudo journalctl -u k3s -f --no-pager

# အဖြစ်များသော ပြုပြင်မှု: ပေါ့တ် ၆၄၄၃ နှင့် ၁၀၂၅၀ တို့ကို ဖိုင်းဝေါက ပိတ်ဆို့မထားကြောင်း သေချာစေပါ
sudo ss -tlnp | grep 6443
```

### Kubernetes API သို့ "Connection refused" ဖြစ်နေသည်
```bash
# K3s API server နားထောင်နေကြောင်း အတည်ပြုရန်
curl -k https://YOUR_VPS_IP:6443/healthz
# ok

# ဖိုင်းဝေါက သင့် IP မှ ပေါ့တ် ၆၄၄၃ ကို ခွင့်ပြုထားကြောင်း စစ်ဆေးပါ
ufw status  # သို့မဟုတ် VPS ပံ့ပိုးပေးသူ ဖိုင်းဝေါ စည်းမျဉ်းများကို စစ်ဆေးပါ
```

### cert-manager webhook မအောင်မြင်ပါ
```bash
kubectl -n cert-manager describe pod -l app=cert-manager-webhook
# အများအားဖြင့် အချိန်ကိုက်ပြဿနာဖြစ်သည် — စက္ကန့် ၆၀ စောင့်ပြီး ပြန်ကြိုးစားပါ
```

## အကျဉ်းချုပ်

သင်၏ ထုတ်လုပ်ရေးဆာဗာသည် ယခုအခါ အဆင်သင့်ဖြစ်နေပါပြီ:
- SSH key ဖြင့်သာ ဝင်ရောက်ခြင်း၊ root ဖြင့် ဝင်ရောက်မှုကို ပိတ်ထားခြင်းနှင့် အလိုအလျောက် လုံခြုံရေး အပ်ဒိတ်များပါရှိသော **Ubuntu 22.04**
- Traefik ingress controller (K3s မူလအတိုင်းမဟုတ်ဘဲ Helm ဖြင့်) ထည့်သွင်းထားသော **K3s**
- လက်ပ်တော့မှ လှမ်းသုံးနိုင်ပြီး GitHub Secret အဖြစ် သိမ်းဆည်းထားသော **Remote `kubectl` အသုံးပြုခွင့်**
- စတိတ်ဂျင်းနှင့် ထုတ်လုပ်ရေး Let's Encrypt ClusterIssuers များပါရှိသော **cert-manager**
- ဖန်တီးပြီး အညွှန်းတပ်ထားသော **`production` namespace**
- ဆာဗာတွင် ထည့်သွင်းပြီး GitHub Secrets တွင် သိမ်းဆည်းထားသော **Deploy SSH key**

နောက်သင်ခန်းစာတွင်၊ ကလပ်စတာအတွင်းရှိ သင့်အက်ပ်၏ လိုချင်သော အနေအထားကို သတ်မှတ်ပေးသည့် Kubernetes manifests များကို (Deployment, Service, Ingress, ConfigMap, Secret) ရေးသားရမည် ဖြစ်ပါသည်။
