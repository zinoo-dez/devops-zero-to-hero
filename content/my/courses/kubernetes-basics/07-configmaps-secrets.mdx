# သင့်ရဲ့ Container Image ထesထဲမှာ Configuration တွေကို ဘယ်တော့မှ ထည့်မတည်ဆောက်ပါနဲ့ (Never Bake Configuration Into Your Container Image)

[12-Factor App](https://12factor.net/config) methodology ရဲ့ အခြေခံမူတစ်ရပ်ကတော့- **configuration တွေကို code ထဲမှာ မဟုတ်ဘဲ environment ထဲမှာ သိမ်းဆည်းရပါမယ်**။

သင့်ရဲ့ database URL ကို Docker image ထဲမှာ hardcode လုပ်ထားမယ်ဆိုရင် environment တစ်ခုချင်းစီ (dev, staging, production) အတွက် image အသီးသီးကို တည်ဆောက်ရပါလိမ့်မယ်။ အဲ့ဒါ ဘာကို ဆိုလိုတာလဲဆိုတော့ environment အမျိုးမျိုးဆီကို code အမျိုးမျိုး ပို့ဆောင်နေတာ ဖြစ်ပြီး — အဲဒါက containerization ရဲ့ မူလရည်မှန်းချက်ကို ဆန့်ကျင်ရာရောက်ပါတယ်။

Kubernetes က configuration တွေထည့်သွင်းဖို့ (injection) resources နှစ်ခုကို ပံ့ပိုးပေးပါတယ်-

| Resource | ဘယ်အရာအတွက်လဲ | etcd ထဲမှာ Encryption လုပ်ထားမှု |
|----------|-----|--------------------|
| **ConfigMap** | အရေးမကြီးတဲ့ config များ: ports, feature flags, service URLs | ❌ Plaintext (စာသားသက်သက်) |
| **Secret** | လျို့ဝှက်ချက်ဒေတာများ: passwords, API keys, TLS certificates | ✅ Base64 (envelope encryption ဖြင့် rest မှာ encrypted လုပ်ထားသည်) |

## ConfigMaps

### ConfigMaps များကို ဖန်တီးခြင်း (Creating ConfigMaps)

```bash
# Method 1: Imperative (literal တန်ဖိုးများမှ တိုက်ရိုက်ဖန်တီးခြင်း)
kubectl create configmap api-config \
  --from-literal=NODE_ENV=production \
  --from-literal=PORT=3000 \
  --from-literal=LOG_LEVEL=info \
  --from-literal=DB_HOST=postgres.production.svc.cluster.local \
  -n production

# Method 2: Imperative (ဖိုင်တစ်ခုမှ — key=filename, value=file content)
kubectl create configmap nginx-config \
  --from-file=nginx.conf=/path/to/nginx.conf \
  -n production

# Method 3: Declarative (ပိုနှစ်သက်ကြသည် — version-controllable လုပ်နိုင်သည်)
kubectl apply -f configmap.yaml
```

```yaml
# configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
  namespace: production
data:
  # Key-value pairs (strings သက်သက်သာ)
  NODE_ENV: "production"
  PORT: "3000"
  LOG_LEVEL: "info"
  DB_HOST: "postgres.production.svc.cluster.local"
  DB_PORT: "5432"
  DB_MAX_CONNECTIONS: "20"
  CACHE_TTL_SECONDS: "300"
  FEATURE_DARK_MODE: "true"

  # Config ไฟล์တစ်ခုလုံးကို တန်ဖိုးတစ်ခုအနေဖြင့် (multi-line string)
  config.json: |
    {
      "environment": "production",
      "rateLimit": {
        "windowMs": 60000,
        "max": 100
      },
      "cors": {
        "origins": ["https://app.yourdomain.com"]
      }
    }

  nginx.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://localhost:3000;
        proxy_set_header X-Real-IP $remote_addr;
      }
    }
```

### Pods များတွင် ConfigMaps များကို အသုံးပြုခြင်း (Using ConfigMaps in Pods)

#### Method 1: Environment Variables အဖြစ် (Keys တစ်ခုချင်းစီ)

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      env:
        - name: NODE_ENV
          valueFrom:
            configMapKeyRef:
              name: api-config     # ConfigMap အမည်
              key: NODE_ENV        # ConfigMap ထဲရှိ key
        - name: PORT
          valueFrom:
            configMapKeyRef:
              name: api-config
              key: PORT
```

#### Method 2: Keys အားလုံးကို Environment Variables အဖြစ် (envFrom)

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      # api-config ထဲရှိ keys အားလုံးသည် environment variables ဖြစ်သွားမည်
      envFrom:
        - configMapRef:
            name: api-config
      # ကျွန်ုပ်၏ app တွင် ယခုအခါ ဤသို့ရှိသည်: NODE_ENV=production, PORT=3000, LOG_LEVEL=info, စသည်ဖြင့်။
```

#### Method 3: Volume တစ်ခုတွင် Mounted လုပ်ထားသော Files အဖြစ်

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      volumeMounts:
        - name: config-volume
          mountPath: /app/config       # Container ထဲရှိ mount လုပ်မည့်နေရာ
          readOnly: true

  volumes:
    - name: config-volume
      configMap:
        name: api-config
        # သီးသန့် keys များကိုသာ files အဖြစ် mount လုပ်ရန် (optional — မပါလျှင်: keys အားလုံး)
        items:
          - key: config.json
            path: config.json          # → /app/config/config.json
          - key: nginx.conf
            path: nginx.conf           # → /app/config/nginx.conf
```

<Callout type="tip" title="Volume-Mounted ConfigMaps များကို အလိုအလျောက် Update လုပ်ပေးသည်">
ConfigMap တစ်ခု ပြောင်းလဲသွားတဲ့အခါ **volume-mounted** လုပ်ထားတဲ့ files တွေဟာ running containers တွေထဲမှာ (စက္ကန့် ၆၀ မှ ၁၂၀ အတွင်း) အလိုအလျောက် update ဖြစ်သွားပါတယ်။ သင့်ရဲ့ app က ဖိုင်ပြောင်းလဲမှုကို စောင့်ကြည့်ပြီး (watch) hot reload လုပ်နိုင်ပါတယ်။

**Environment variable** ConfigMaps (`envFrom`) တွေကတော့ အလိုအလျောက် update မဖြစ်ပါဘူး — ပြောင်းလဲမှုတွေကို သိရှိစေရန် pod ကို restart လုပ်ပေးရပါမယ်။
</Callout>

## Secrets

Secrets တွေက လျို့ဝှက်ဒေတာတွေကို သိမ်းဆည်းပေးပါတယ်။ Kubernetes က config တွေကို etcd ထဲမှာ **envelope encryption** သုံးပြီး (configure လုပ်ထားချိန်မှာ) rest မှာ encrypt လုပ်ပေးပြီး အတိအကျညွှန်းဆိုထားတဲ့ pods တွေကိုသာ ဖွင့်ပြပေးပါတယ်။

### Secrets များကို ဖန်တီးခြင်း (Creating Secrets)

```bash
# Method 1: Literal တန်ဖိုးများမှ generic secret ဖန်တီးခြင်း
kubectl create secret generic postgres-secret \
  --from-literal=POSTGRES_USER=appuser \
  --from-literal=POSTGRES_PASSWORD="$(openssl rand -base64 32 | tr -d '=')" \
  --from-literal=POSTGRES_DB=myapp \
  -n production

# Method 2: Files မှ (TLS certs, SSH keys တွေအတွက် အသုံးဝင်သည်)
kubectl create secret generic tls-secret \
  --from-file=tls.crt=/path/to/cert.crt \
  --from-file=tls.key=/path/to/cert.key \
  -n production

# Method 3: TLS Secret (အထူးအမျိုးအစား၊ Ingress controllers တွေက သိရှိနိုင်သည်)
kubectl create secret tls my-tls-secret \
  --cert=/path/to/cert.crt \
  --key=/path/to/cert.key \
  -n production

# Method 4: Docker registry credentials (private registries အတွက်)
kubectl create secret docker-registry ghcr-pull-secret \
  --docker-server=ghcr.io \
  --docker-username=YOUR_USERNAME \
  --docker-password=YOUR_GITHUB_PAT \
  -n production
```

```yaml
# secret.yaml (declarative — ဒါပေမဲ့ passwords တွေကို plaintext နဲ့ ဘယ်တော့မှ commit မလုပ်ပါနဲ့!)
# ဤ template ကိုသုံးပါ၊ တန်ဖိုးများကို base64 ဖြင့် ဖြည့်ပါ သို့မဟုတ် Sealed Secrets / External Secrets ကို အသုံးပြုပါ
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
  namespace: production
type: Opaque    # Generic secret
data:
  # တန်ဖိုးများသည် base64 encoded ဖြစ်ရပါမည်
  # echo -n "mypassword" | base64
  POSTGRES_PASSWORD: bXlwYXNzd29yZA==
  API_KEY: c2VjcmV0LWtleS12YWx1ZQ==
stringData:
  # တနည်းအားဖြင့် stringData ကိုသုံးပါ — K8s က သင့်အတွက် base64-encode လုပ်ပေးပါလိမ့်မည်
  DATABASE_URL: "postgres://appuser:password@postgres:5432/myapp"
```

<Callout type="caution" title="Secrets များကို Git ထဲသို့ ဘယ်တော့မှ commit မလုပ်ပါနဲ့">
တကယ့်တန်ဖိုးတွေပါတဲ့ `secret.yaml` ကို private repository ထဲမှာတောင် Git commit **ဘယ်တော့မှ မလုပ်ရပါဘူး**။ အဲ့ဒီတန်ဖိုးတွေက base64-encoded သာဖြစ်ပြီး (encrypted မဟုတ်ပါ) `base64 -d` နဲ့ အလွယ်တကူ decode လုပ်လို့ရပါတယ်။

Production အတွက် ဒီနည်းလမ်းတွေထဲက တစ်ခုကို အသုံးပြုပါ:
- **Sealed Secrets** (Bitnami) — cluster-specific key တစ်ခုနဲ့ secrets တွေကို encrypt လုပ်ပါ; commit လုပ်လို့ လုံခြုံပါတယ်
- **External Secrets Operator** — AWS Secrets Manager, Vault, သို့မဟုတ် GCP Secret Manager ကနေ secrets တွေကို sync လုပ်ပါ
- **kubectl create secret** ကို CI/CD မှာ imperatively သုံးပါ (Git ထဲမှာ ဘယ်တော့မှ မသိမ်းပါ)
- **GitHub Actions Secrets** → `kubectl create secret` ကို env vars အဖြစ် ပေးပို့ပါ
</Callout>

### Pods များတွင် Secrets များကို အသုံးပြုခြင်း (Using Secrets in Pods)

#### Method 1: Environment Variables တစ်ခုချင်းစီ အဖြစ်

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: app-secret      # Secret အမည်
              key: DATABASE_URL     # Secret ထဲရှိ key
        - name: API_KEY
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: API_KEY
              optional: false       # key မရှိရင် pod စတင်တာ ပျက်ကွက်ပါမယ်
```

#### Method 2: Secret Keys အားလုံးကို Env Vars အဖြစ်

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      envFrom:
        - secretRef:
            name: app-secret
```

#### Method 3: Files အဖြစ် Mounted လုပ်ခြင်း (TLS certs နှင့် SSH keys အတွက် အကြံပြုသည်)

```yaml
spec:
  containers:
    - name: api
      image: my-api:v2
      volumeMounts:
        - name: tls-certs
          mountPath: /etc/ssl/certs
          readOnly: true

  volumes:
    - name: tls-certs
      secret:
        secretName: my-tls-secret
        defaultMode: 0400    # File permissions: owner read-only
        items:
          - key: tls.crt
            path: server.crt   # → /etc/ssl/certs/server.crt
          - key: tls.key
            path: server.key   # → /etc/ssl/certs/server.key
```

## လက်တွေ့ကမ္ဘာ ဥပမာ- ConfigMap + Secret ပါဝင်သော Full App Stack

```yaml
# api-with-config.yaml
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
  namespace: production
data:
  NODE_ENV: "production"
  PORT: "3000"
  LOG_LEVEL: "info"
  DB_HOST: "postgres.production.svc.cluster.local"
  DB_MAX_CONNECTIONS: "20"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: ghcr.io/youruser/api:v2.0.1
          ports:
            - containerPort: 3000
          
          # အရေးမကြီးတဲ့ config: ConfigMap ထဲက keys အားလုံး
          envFrom:
            - configMapRef:
                name: api-config
          
          # အရေးကြီးတဲ့ config: Secret ထဲက key တစ်ခုချင်းစီ
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: app-secret
                  key: DATABASE_URL
            - name: JWT_SECRET
              valueFrom:
                secretKeyRef:
                  name: app-secret
                  key: JWT_SECRET
          
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits: { cpu: "500m", memory: "512Mi" }
          
          readinessProbe:
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 5
            periodSeconds: 10
```

```bash
# Secret ကို ဦးစွာ deploy ပါ (Deployment က ဒါမပါရင် စတင်လို့မရပါ)
kubectl create secret generic app-secret \
  --from-literal=DATABASE_URL="postgres://appuser:mypassword@postgres.production.svc.cluster.local:5432/myapp" \
  --from-literal=JWT_SECRET="$(openssl rand -base64 48)" \
  -n production

# ထို့နောက် app ကို deploy ပါ
kubectl apply -f api-with-config.yaml

# pod ထဲမှာ env vars တွေ ရနိုင်မရနိုင် စစ်ဆေးပါ
kubectl exec -n production deployment/api -- env | grep -E "NODE_ENV|PORT|LOG_LEVEL|DATABASE"
# NODE_ENV=production
# PORT=3000
# LOG_LEVEL=info
# DATABASE_URL=postgres://appuser:mypassword@postgres.production:5432/myapp
```

## ConfigMaps နှင့် Secrets များကို စစ်ဆေးခြင်း (Inspecting ConfigMaps and Secrets)

```bash
# ConfigMap ရဲ့ data ကို ကြည့်ရန် (plaintext)
kubectl get configmap api-config -n production -o yaml

# Secret တန်ဖိုးကို decode လုပ်ရန် (base64)
kubectl get secret app-secret -n production -o jsonpath='{.data.DATABASE_URL}' | base64 -d
# postgres://appuser:mypassword@postgres:5432/myapp

# Secret ထဲရှိ data အားလုံးကို ကြည့်ရန် (decoded)
kubectl get secret app-secret -n production -o json | \
  jq -r '.data | to_entries[] | "\(.key): \(.value | @base64d)"'

# namespace တစ်ခုထဲရှိ secrets အားလုံးကို listing လုပ်ရန်
kubectl get secrets -n production
# NAME                    TYPE                DATA   AGE
# app-secret              Opaque              2      5m
# ghcr-pull-secret        kubernetes.io/dockerconfigjson   1   10m
# my-tls-secret           kubernetes.io/tls   2      3d
# default-token-xxx       kubernetes.io/service-account-token   3   30d
```

## Production Best Practices

### 1. တကယ့် Production အတွက် External Secrets Operator ကို အသုံးပြုပါ

Secrets manager တစ်ခုကနေ secrets တွေကို sync လုပ်ခြင်းက developers တွေအနေနဲ့ တကယ့် production passwords တွေကို ဘယ်တော့မှ မမြင်ရအောင် လုပ်ပေးပါတယ်:

```yaml
# ExternalSecret: AWS Secrets Manager မှ ဆွဲယူသည်
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secret
  namespace: production
spec:
  refreshInterval: 1h              # တစ်နာရီတစ်ကြိမ် AWS SM မှ Resync လုပ်သည်
  secretStoreRef:
    name: aws-secrets-manager
    kind: SecretStore
  target:
    name: app-secret               # ပုံမှန် K8s Secret တစ်ခုကို ဖန်တီးသည်
    creationPolicy: Owner
  data:
    - secretKey: DATABASE_URL      # K8s Secret ထဲရှိ key
      remoteRef:
        key: prod/myapp/db         # AWS Secrets Manager secret အမည်
        property: url              # secret ထဲရှိ JSON property
```

### 2. Downtime မရှိဘဲ Secrets များကို Rotate လုပ်ပါ

```bash
# secret တန်ဖိုးကို update လုပ်ပါ (rotation ပြီးနောက် password အသစ်)
kubectl create secret generic app-secret \
  --from-literal=DATABASE_URL="postgres://appuser:NEWPASSWORD@postgres:5432/myapp" \
  -n production \
  --dry-run=client -o yaml | kubectl apply -f -

# env var တန်ဖိုးအသစ်ကို ရရှိစေရန် rolling restart ကို trigger လုပ်ပါ
kubectl rollout restart deployment/api -n production
```

### 3. Namespace Isolation

Secrets တွေဟာ namespace-scoped ဖြစ်ပါတယ်။ `staging` namespace ထဲက pod တစ်ခုဟာ `production` namespace ထဲက secrets တွေကို ဝင်ရောက်ကြည့်ရှုလို့ မရပါ:

```bash
# namespace တစ်ခုချင်းစီမှာ တူညီတဲ့ secret ကို သီးခြားစီ ဖန်တီးပါ
kubectl create secret generic app-secret --from-literal=... -n staging
kubectl create secret generic app-secret --from-literal=... -n production
```

## အနှစ်ချုပ် (Summary)

ConfigMaps နှင့် Secrets တို့သည် configuration များကို container images များမှ ခွဲထုတ်ပေးသည်:
- **ConfigMaps**: အရေးမကြီးသော key-value pairs များနှင့် config files များကို သိမ်းဆည်းသည် — `envFrom`, သီးသန့် `env[].valueFrom.configMapKeyRef`, သို့မဟုတ် volume mounts များမှတစ်ဆင့် ထည့်သွင်းပေးသည်
- **Secrets**: အရေးကြီးသော လျို့ဝှက်ဒေတာများကို သိမ်းဆည်းသည် — တူညီသော ထည့်သွင်းသည့်နည်းလမ်းများ; တန်ဖိုးများကို YAML ထဲတွင် base64-encoded ဖြင့် ထားရှိသည်
- **Volume-mounted ConfigMaps** များသည် running pods တွေထဲမှာ အလိုအလျောက် update ဖြစ်သွားပါတယ်; env var ConfigMaps တွေကတော့ pod restart လုပ်ဖို့ လိုအပ်ပါတယ်
- **Secrets များကို Git ထဲသို့ ဘယ်တော့မှ commit မလုပ်ပါနဲ့** — Sealed Secrets, External Secrets Operator ကို သုံးပါ သို့မဟုတ် CI/CD မှာ imperatively ဖန်တီးပါ
- Production တွင် AWS Secrets Manager, GCP Secret Manager, သို့မဟုတ် HashiCorp Vault တို့မှ sync လုပ်ရန် **External Secrets Operator** ကို အသုံးပြုပါ

နောက်လာမည့် သင်ခန်းစာတွင်, သင့်ရဲ့ application ကို hostname နှင့် URL path အလိုက် HTTP/HTTPS traffic များကို routing လုပ်ပေးမည့် **Ingress Controller** တစ်ခုနှင့်အတူ အင်တာနက်ပေါ်သို့ ချိတ်ဆက်ပြသပေးသွားပါမည်။
